## 1. Plan récapitulatif

### 1.1 Le diagnostic en 8 lignes

1. **Le socle est sain** : isolation multi-commune testée, RLS partout, feeds paginés, fan-out corrigé, sanitisation HTML, headers de sécurité, ton éthique, pas de dark patterns.
2. **Un correctif de sécurité est dû immédiatement** : Next.js 16.2.6 est concerné par des avis **critiques** (dont l'optimisation d'images, que vous utilisez) ; la désinscription e-mail peut être déclenchée sur n'importe quel compte.
3. **Le risque RGPD n°1 est l'écart entre les documents et le système** : la politique et le DPA ne décrivent ni la visibilité de l'adresse entre voisins (voulue), ni les coordonnées GPS, ni Infomaniak, ni les durées réellement appliquées ; la RLS expose en outre la ligne `memberships` complète (GPS exact compris) via l'API.
4. **La suppression de compte promet plus qu'elle ne fait** (messages, journaux, file d'e-mails) et contredit la politique (30 jours / 2 ans) ; pas d'export de données, pas de purge, pas de procédure de violation.
5. **Plusieurs mutations ne sont pas atomiques** (quitter une commune, inscription, invitation, plafond d'essai) et certaines erreurs sont avalées ; la « suppression définitive » d'une conversation ne supprime rien.
6. **La performance est correcte à l'échelle actuelle** (1 commune, 50 inscrits). Les gains sont sur le coût par navigation (accueil, `router.refresh()`, cartes, tableaux de bord) plutôt que sur un point bloquant.
7. **L'onboarding perd des gens à trois endroits** : double barrière e-mail + reconnexion, tutoriel de 4 écrans sans « Passer », première annonce très lourde.
8. **Aucune mesure d'activation n'existe** (`track()` n'est appelé nulle part) : on ne peut pas savoir où les gens décrochent.

### S1 — Désinscription : n'importe qui peut désinscrire n'importe quel compte (élevée)

| Urgence | Effort | Régression | Vérifié |
| --- | --- | --- | --- |
| **P0** | 1–2 h | Faible | Oui |

**Constat.** `app/(public)/unsubscribe/actions.ts` : la Server Action `unsubscribeFromEmails(userId)` écrit avec le client `service_role` sur l'`userId` reçu, **sans** revérifier le jeton. La page vérifie bien le jeton, mais une Server Action est un point d'entrée HTTP appelable directement. Un UUID connu suffit pour couper les e-mails d'un tiers (impact : consentement détourné, relances manquées).

**Patch.**

```ts
// app/(public)/unsubscribe/actions.ts
export async function unsubscribeFromEmails(token: string) {
  // Never trust a client-supplied user id: derive it from the signed token.
  const payload = verifyUnsubscribeToken(token);
  if (!payload) return { success: false };
  const service = await createServiceClient();
  const { error } = await service
    .from("user_notification_preferences")
    .upsert({ user_id: payload.userId, email_lifecycle_enabled: false }, { onConflict: "user_id" });
  return { success: !error };
}
```

Le bouton passe `token` au lieu de `userId`. Ajouter un test unitaire (jeton invalide, expiré, valide).

### S2 — Secrets : comparaisons non constantes et clé réutilisée (élevée)

| Urgence | Effort | Régression | Vérifié |
| --- | --- | --- | --- |
| P0/P1 | 2–3 h | Faible | Oui |

**Constat.**

- `app/api/cron/lifecycle/route.ts` et `email-sender/route.ts` : `authHeader === \`Bearer ${secret}\`` (comparaison non constante).
- `lib/email/unsubscribe-token.ts` : `signature !== expectedSignature`, et le HMAC est dérivé de la **clé `service_role`**. Faire tourner cette clé (ce qui est une bonne pratique après incident) invaliderait tous les liens de désinscription déjà envoyés.

**Patch.** Utiliser `crypto.timingSafeEqual` sur des buffers de même longueur (helper partagé dans `lib/utils/`), introduire `UNSUBSCRIBE_HMAC_SECRET` (avec version dans le jeton pour migrer sans casser les anciens liens), exiger `CRON_SECRET` ≥ 32 octets aléatoires.

### S3 — Limitation de débit : en mémoire et absente des endpoints coûteux (élevée)

| Urgence | Effort | Régression | Vérifié |
| --- | --- | --- | --- |
| P1 | 8–12 h | Moyen | Oui (limiteur) / Relevé (endpoints) |

**Constat.** `lib/utils/rate-limit.ts` est un `Map` en mémoire : remis à zéro à chaque déploiement, inefficace dès deux instances. *Réévaluation après vos réponses : avec une seule instance sur le VPS, la limite fonctionne entre deux déploiements ; l'urgence tient donc surtout aux endpoints qui n'en ont aucune (inscription, invitations, upload) et au fait qu'Infomaniak applique ses propres quotas d'envoi. Appliquer : inscription (IP + e-mail), invitations (compte/commune/jour), upload (compte/heure), analytics (compte/min). Ajouter un plafond d'invitations par commune.

### S14 — Compte seed et identifiants de développement (élevée si le seed a été joué en prod)

| Urgence | Effort | Régression | Vérifié |

| **P0 (vérification)** | 0,5 h | Nul | Oui (documentation) |

**Ce que fait `supabase/seed.sql`.** C'est un jeu de données de **développement local**, joué automatiquement par `supabase db reset` (déclaré dans `supabase/config.toml`). Il :

1. crée (ou **écrase**, `ON CONFLICT (insee_code) DO UPDATE`) la commune pilote Les Authieux (INSEE 27027) ;
2. crée deux comptes dans `auth.users` avec le mot de passe connu `VieLocaleDev2026!` et l'e-mail déjà confirmé : le vôtre, `dubois.gwendoline@hotmail.fr`, avec `is_platform_admin = true` (accès à tout le backoffice), et `mairie.les-authieux@tous-voisins.dev` (référent mairie) ;
3. leur donne une adhésion active dans la commune pilote.

Les comptes sont créés avec des identifiants fixes et, en cas de conflit, le script **remplace l'e-mail, le mot de passe et le profil** (`encrypted_password = excluded.encrypted_password`). Le README invite à l'exécuter « sur un projet cloud distant (dev uniquement) » : si cela a été fait sur la production, le mot de passe de votre compte super admin est public dans le dépôt ; si c'est rejoué, il est remis à cette valeur. À noter : `.env.prod` est bien ignoré par Git, jamais commité et exclu de l'image Docker (je n'ai pas ouvert son contenu).

**Vérification à faire dans le SQL Editor de Supabase (production), en lecture seule :**

```sql
-- Does any seeded account still exist, and does it still use the dev password?
select
  email,
  created_at,
  last_sign_in_at,
  (encrypted_password = extensions.crypt('VieLocaleDev2026!', encrypted_password)) as password_is_dev_default
from auth.users
where email in ('dubois.gwendoline@hotmail.fr', 'mairie.les-authieux@tous-voisins.dev');
```

- Une ligne `mairie.les-authieux@tous-voisins.dev` : compte fictif sur une commune réelle ; à supprimer.
- Aucune ligne ou `false` : rien à faire côté base, mais retirer le mot de passe du README et de `AGENTS.md`.

**Patch.**

1. Retirer l'adresse personnelle et le mot de passe des docs ; utiliser des comptes `@example.invalid`.
2. Faire échouer `seed.sql` hors local (par exemple vérifier `current_setting('app.env', true) = 'local'` en tête de script) et retirer l'instruction « exécuter sur un projet cloud » du README.

## 3. RGPD (cadre français, CNIL)

> **Bilan :** la structure juridique est bien pensée (commune = responsable de traitement, éditeur = sous-traitant, CGU + politique, désinscription). Les écarts viennent du **fossé entre le texte et le code** : ce que la politique promet (30 jours, 2 ans, effacement) n'est pas ce que le système fait, et quelques mécanismes obligatoires manquent (export, purge, violation).

### R1 — Adresse de domicile visible des voisins : voulu, mais non décrit et trop large techniquement (moyenne)

| Urgence | Effort | Régression | Vérifié |
| --- | --- | --- | --- |
| P1 (texte) / P2 (technique) | 2 h (texte) + 4–6 h (requêtes) ; option RLS 16–24 h | Nul / Faible / Élevé | Oui (policy RLS et requêtes lues ; non testé avec deux comptes) |

**Constat (après votre réponse « c'est voulu »).** Rendre la rue d'un auteur visible de ses voisins est un choix produit défendable pour une app d'entraide de proximité. Restent deux écarts :

1. **Transparence.** La politique de confidentialité (art. 5) ne mentionne que « le prénom et les informations qu'un Utilisateur choisit de faire figurer dans une annonce ». Elle ne dit pas que **l'adresse du domicile (rue) est visible des autres habitants de la commune**, ni que les coordonnées GPS sont calculées et stockées. Les habitants doivent le savoir **avant** de s'inscrire (art. 13).
2. **Minimisation technique.** `memberships_select` (`20260810150300_rls_auth_uid_policies_session.sql`) autorise la lecture de la **ligne entière** (rue, lieu-dit, code postal, `address_lat`, `address_lng` exacts) par tout résident actif de la commune, via l'API REST. L'interface n'affiche que la rue, mais un résident curieux peut obtenir la **position GPS précise** de chaque voisin. Les requêtes de liste (`announcements.ts:124,168`, `initiatives.ts`, `profile-content.ts`) joignent aussi `address_lat/lng` de l'auteur pour chaque carte, ce qui alourdit les réponses sans servir à l'affichage.

### R6 — Durées de conservation : peu de purges (élevée)

| Urgence | Effort | Régression | Vérifié |
| --- | --- | --- | --- |
| P1 | 12–20 h | Moyen | Oui (cron lu) |

**Constat.** Seules les annonces et conversations archivées sont purgées (30 jours). **Aucune purge** pour : `audit_logs` (IP + user-agent + e-mail), `email_queue`, `analytics_events`, `notifications` (déjà suivi sujet 8), `support_requests`, `commune_interest_leads`, `neighbor_invites`, `push_subscriptions` expirées, **comptes créés mais jamais confirmés** (le compte est créé avant la vérification de l'e-mail).

**Principe de choix.** Le RGPD ne fixe presque jamais de chiffre : il demande que la durée soit **justifiée par la finalité** (art. 5.1.e) et **annoncée** (art. 13.2.a). La bonne durée est donc la plus courte qui permette encore de faire ce pour quoi la donnée existe. Trois cas de figure :

1. **Une loi impose une durée minimale** : on la respecte, dans une base d'archive à accès restreint, pas dans l'application courante.
2. **Une donnée sert à la sécurité ou à la preuve** : on garde le temps pendant lequel un incident ou un litige peut raisonnablement surgir, en s'alignant sur les repères CNIL.
3. **Une donnée n'est qu'un déchet technique** (file d'e-mails envoyés, invitation périmée) : on la supprime dès que la fonction est accomplie, plus une marge pour le dépannage.

**Durées recommandées et justification**

| Donnée | Durée | Pourquoi celle-là |
| --- | --- | --- |
| **Compte créé mais jamais confirmé** | **7 jours** (relance à J+1, suppression à J+7) | Un e-mail non confirmé en une semaine ne le sera plus ; la personne n'a jamais utilisé le service, on n'a aucune raison de garder son nom, son adresse et ses coordonnées GPS. Supprimer vite réduit aussi la cible en cas de fuite. |
| **`audit_logs`** (IP, user-agent, actions) | **12 mois**, puis suppression (ou anonymisation si on veut des statistiques) | Repère CNIL pour les journaux de sécurité : 6 à 12 mois, 12 mois étant le plafond courant pour un usage sécurité/traçabilité. C'est aussi la durée du décret 2021-1362 pour les données techniques de connexion (1 an), ce qui met l'éditeur en règle avec la LCEN sans sur-conserver. Au-delà, l'IP d'un habitant ne sert plus à rien pour détecter un abus. |
| **`email_queue` envoyée ou annulée** | **30 jours** | Sert à vérifier qu'un e-mail est bien parti et à déboguer un problème de relance. Un mois couvre largement les réclamations (« je n'ai jamais reçu… ») ; le contenu (`variables`) comporte des noms et des liens signés : inutile de les conserver. Les lignes `failed` peuvent être gardées 90 jours pour analyse. |
| **`neighbor_invites` non acceptée** | **Suppression de l'e-mail du tiers 30 jours après expiration** (l'invitation expire déjà à 30 jours, donc ~60 jours après l'envoi) | L'e-mail appartient à une personne qui n'a rien demandé (art. 14). La CNIL, pour le parrainage, admet une utilisation **unique** : une fois l'invitation expirée, aucune finalité ne justifie de la garder. On conserve la ligne sans l'e-mail (statistique d'invitations, protection contre le spam). |
| **`push_subscriptions`** | Suppression dès un retour **404/410** du service push, et après **6 mois sans succès d'envoi** | Un abonnement mort est un déchet technique ; le garder fait travailler le cron pour rien. |
| **`notifications`** (in-app) | **90 jours** (si le centre de notifications est construit) ; sinon arrêter d'écrire | Une notification de 3 mois n'a plus de valeur pour l'habitant ; la table grossit à chaque relance (roadmap sujet 8). |
| **`support_requests`** | **12 mois après clôture** | Temps raisonnable pour une réclamation qui rebondit ou un suivi de qualité ; la CNIL retient souvent 12 mois pour la gestion des réclamations hors contentieux. |
| **`commune_interest_leads`** (e-mails de personnes dont la commune n'est pas ouverte) | **24 mois après le dernier contact**, puis suppression | Repère CNIL pour les prospects non clients : 3 ans maximum ; 2 ans suffisent ici, le temps pour une commune de délibérer et de signer. Prévenir ces personnes à l'ouverture, puis supprimer. |
| **`analytics_events`** (si activé, voir U6) | **13 mois** pour les événements bruts, agrégats anonymes conservés sans limite | 13 mois est le plafond CNIL pour la mesure d'audience exemptée de consentement (il couvre une année complète plus la comparaison d'un mois sur l'autre). Les totaux par commune et par mois ne sont plus des données personnelles. |
| **Messages privés** | Durée de vie du compte ; **suppression à la suppression du compte de l'expéditeur** (ou anonymisation du texte), et purge des conversations archivées déjà en place (30 jours) | C'est le point qui contredit aujourd'hui le droit à l'effacement (R2). Le destinataire garde son propre fil tant que son compte existe, mais le texte d'un compte supprimé ne doit plus être lisible. |
| **Données d'identification après suppression de compte** (nom, prénom, adresse, e-mail) | **Registre séparé, 12 mois** (ou 5 ans si un juriste confirme que l'art. 6-II LCEN vous est applicable comme hébergeur de contenus) | C'est la seule durée réellement imposée par un texte, mais elle ne doit s'appliquer qu'aux données d'identification, dans une table isolée à accès restreint, pas dans l'application. Aujourd'hui la politique dit 2 ans et le code 0 jour : les deux sont faux. |
| **Contenus publiés** (annonces, événements, initiatives) | Archivés puis purgés à **30 jours** (déjà en place) ; conservés tant que le compte existe sinon | Cohérent et déjà appliqué. |
| **Sauvegardes** | **30 jours** glissants ; **90 jours** après la fin d'un contrat de commune | Reprend l'engagement du DPA (art. 8). Au-delà d'un mois, une sauvegarde ne sert plus à réparer un incident et devient un stock de données qu'on ne peut plus purger. |

**Ce que ces choix impliquent.** Les durées courtes (7 jours, 30 jours) protègent surtout **vous** : moins de données, c'est moins de dégâts si la base fuit, et une réponse plus simple aux demandes d'accès. Les durées de 12 mois sont des **compromis sécurité / vie privée** adossés aux repères CNIL : elles se défendent devant un contrôleur. La seule durée longue (identification après suppression) est **subie**, pas choisie, et doit rester cantonnée.

**Patch.** Une phase cron « rétention » avec les durées centralisées dans `lib/constants/retention.ts`, un test par règle (une ligne à J-1 survit, une ligne à J+1 disparaît), et le même tableau recopié dans la politique de confidentialité (art. 7) et dans l'annexe du DPA. Sans cette mise à jour des textes, les purges ne suffisent pas : c'est l'écart texte / système qui est sanctionné.

| Urgence | Effort | Régression | Vérifié |

## 5. Performance

> **Bilan :** l'architecture est saine (feeds paginés par curseur, RPC pour la messagerie et les compteurs, Leaflet en import dynamique, Cloudinary + `next/image`, service worker limité au push). À 1 commune et 50 inscrits, rien n'est bloquant. Les gains restants portent sur le **coût par navigation**, les **charges utiles de liste** et les **tableaux de bord**. Plusieurs sujets sont **déjà suivis** dans `docs/scaling-roadmap.md` (index FK, `listUsers`, fan-out, badges, 10a/10c/10d, 5 phase 2, 7, 8, 9).

### Où ça peut paraître lent

| Écran | Cause probable | ID |
| --- | --- | --- |
| Toute navigation résidente | Auth validée deux fois (proxy + serveur) puis profil + adhésions avant d'afficher le shell | P2, P7 |
| Accueil | 8 requêtes parallèles, puis annonce mise en avant, puis jusqu'à 3 COUNT annonces | P1 |
| Ouverture d'une conversation | `router.refresh()` complet pour mettre à jour un badge | P2 |
| Vue carte annonces / initiatives | Jusqu'à 500 lignes en `select('*')` avec description HTML et adresse de l'auteur | P3 |
| Dashboard mairie | Jusqu'à 5 000 horodatages ×4 agrégés en JavaScript | P6 |

### Où la bande passante part

1. **Cartes annonces/initiatives** (P3) : 500 × description + auteur complet ; le retrait des adresses (R1 phase 1) réduit aussi la charge.
2. **`select('*')`** dans la session (`lib/auth/session.ts`) : toutes les colonnes d'adhésion + `settings` de la commune à chaque garde.
3. **`router.refresh()`** : retélécharge la page RSC et le shell à chaque ouverture de fil.
4. **`count: 'exact'`** sur chaque page et chaque « charger plus ».
5. **Images** : bien traitées (Cloudinary, `next/image`) ; seul l'aperçu local du dropzone est un `<img>` brut.

### Requêtes inutiles ou redondantes

- Triple COUNT annonces sur l'accueil → une RPC (P1).
- `count: 'exact'` répété (P5).
- Table `notifications` alimentée à chaque notification **sans aucune lecture** dans l'UI : coût d'écriture et de stockage pour une valeur nulle tant que le centre de notifications n'existe pas (P11, lié à U5).
- `shouldSend` : une requête par e-mail dans le cron (P10).
- Analytics : pipeline présent mais non appelé (`track()`), donc pas de coût actuel, mais route sans limite de débit (S3).

## 7. Expérience de participation, rétention et partage

### Ce qui fonctionne déjà (à préserver)

- **Ton chaleureux** et aligné avec la charte ; messages de remerciement et bannière de réussites **basés sur de vraies données** (pas de faux compteurs, pas de fausse urgence).
- **Aucun dark pattern repéré** : pas de série à ne pas casser, pas de culpabilisation, « Non, merci » neutre pour les notifications, désinscription lifecycle opérante, snooze des rappels de contenu.
- **Hero d'accueil qui s'adapte** : s'il y a des demandes aujourd'hui, il invite à y répondre ; sinon, à proposer.
- **Relances par fenêtres de temps, idempotentes**, et invitation par jeton robuste.

### Recommandations
